# File organization — plan (grilled 2026-10-17)

Status: F6 committed, F7 in progress (one-by-one, autonomous
review-loop per slice, user decides ties).

## Goal

All source files live in business folders; no file stays over
1000 lines. Moves are pure (no code change); splits move code
between files without behavior change. Namespaces stay flat.

## Rules (grilled, agreed)

- Folders organize FINDING, not identity: namespaces stay
  `MushTown.Client` / `MushTown.Shared` / ... (Q6 option A).
- Moves and splits never share a commit: move commits are
  rename-only (review skims), split commits get full review.
- Each domain's loader moves with its split file, so a later
  lazy-load change touches one file.
- ID lists live in data, not code (volume growth: hundreds of
  skills, thousands of maps, tens of thousands of items).
- Deferred, NOT this phase: lazy loading / manifest / pack,
  asset-dir sharding (runtime perf, separate scope).

## Client (Q2 agreed)

- `Core/`: Program, Scene, Audio, RollLog (move).
- `Game/`: MushTownGame.cs -> Loop (Update/Draw/shot), Combat
  (swing/skill/cast), Mobs, Drops, Peers (split).
- `Screens/`: Menu.cs -> Saves, Server, Chars, Job, Setup (split).
- `Panels/`: Hud.cs -> HudBar (plate/hpmp/exp/quickslot/tracker/
  bossbar/minimap), BagPanels (inv/stat/skill), QuestPanels
  (quest/settings/shop/talk) (split).
- `Quest/`: Quest.cs (move). `Ui/`: Widgets, UiText, NameTag
  (move). `World/`: CameraComp, MobArt, PeerArt, MapArt (move).
- All six long-file hosts are `partial MushTownGame`: splits
  move methods between partials, zero API risk.
